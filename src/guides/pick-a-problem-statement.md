The problem you choose decides most of what happens next. A good one gives the team a clear target, a demo that explains itself and a story judges remember. A weak one leads to a weekend of building features around an idea nobody can describe in one sentence.

You do not need a brilliant idea. You need a real problem, sized for the time you have, that you can show working.

## Start from the constraints

Before brainstorming, write down what limits you:

- **Time.** How many working hours does the team really have, after sleep, food, talks and travel?
- **Skills.** What can the team build confidently without learning a new stack from scratch?
- **Tracks and rules.** Does the event set themes, required technologies or sponsor challenges?
- **Judging criteria.** What will actually be scored? Impact, technical execution, design and presentation are common.

Ideas that fight these constraints rarely make it to a working demo.

## Problem first, solution second

Describe the problem without mentioning your solution. Three questions help:

1. **Who has this problem?** Name a specific person or group, not "everyone".
2. **What is painful about it today?** Time lost, money spent, errors made, people excluded.
3. **How would you know it is solved?** A number goes down, a task gets faster, a step disappears.

If you cannot answer all three, keep looking. If you can, write it as one sentence:

> **[Who]** struggles to **[do what]** because **[why]**. We will **[approach]** so that **[outcome]**.

This sentence becomes the first line of your pitch and of your submission.

## Size it for the clock

The most common mistake is choosing something too big. A useful test: can you describe a single path through the product that a judge could watch in under a minute? That path is your core. Everything else is optional.

Cut scope until the core can be built, tested and demoed with time to spare. You can always describe the bigger vision in the pitch; you cannot demo what is not built.

## Use the event's own prompts

Tracks and sponsor challenges exist because someone wants to see work in that area, and they often come with their own prizes. Reading them closely can turn up:

- problems the organisers already know are real,
- APIs, datasets or hardware you can use for free,
- people at the event who can answer questions about the domain.

If the event publishes official problem statements, as some national and university hackathons do, read the full statement, note every constraint it sets and ask the organisers about anything ambiguous early.

## Check that the building blocks work

Many ideas depend on something outside your control: an API, a dataset, a device, an account approval. Test these in the first hour:

- Can you get an API key today, and are there rate limits?
- Is the dataset available, clean enough and allowed for this use?
- Does the hardware arrive in time, and does it work with your laptop?

If a dependency fails, switch early. Changing direction in hour two is cheap; in hour twenty it is not.

## See what already exists

A quick search often shows the idea has been built before. That is not a reason to drop it, but it changes the question to "what would we do differently?" Browsing the public project galleries of past events on the same platform is a fast way to see what judges have already seen many times.

## Score your shortlist

When the team has three or four candidates, score each from 1 to 5:

| Criterion | What to ask |
| --- | --- |
| Pain | Would the person with this problem care? |
| Demo | Can we show it working in under a minute? |
| Feasibility | Can we build the core in about half the time we have? |
| Fit | Does it match the theme, tracks and judging criteria? |
| Energy | Do we actually want to work on it all weekend? |

Pick the highest total, unless one idea scores very low on feasibility. A feasible good idea beats an ambitious one that never runs.

## Traps to avoid

- **A solution looking for a problem.** Starting from a technology you want to use and inventing a reason later shows in the pitch.
- **A problem too broad to finish.** "Fix healthcare" is a theme, not a problem statement.
- **Depending on data you do not have.** If the demo needs real user data, plan how you will get safe sample data instead.
- **Changing ideas late.** Set a cut-off (for example, the end of the first evening) after which the idea is fixed.

Once the problem is clear, [plan the hours](/guides/plan-48-hours/) and make sure the [team](/guides/form-a-team-that-works/) knows who is building what.
