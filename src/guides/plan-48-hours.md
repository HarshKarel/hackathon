Forty-eight hours feels like a lot of time on Friday evening and very little on Sunday morning. Teams that finish well are rarely the ones who work the most hours. They protect three things from the start: a working demo, a complete submission and enough sleep to present clearly.

This plan assumes a 48-hour event. For 24 or 36 hours, keep the same order and shrink each block.

## Before the clock starts

- Read the rules, the judging criteria and the submission requirements, including any video length limit.
- Check the deadline in your own time zone. Every event page on hackathon.so shows it converted for you.
- Set up accounts, API keys and development tools.
- Agree on the team's goal and roles. See [how to form a team that works](/guides/form-a-team-that-works/).

## The plan

| Hours | Focus | Done when |
| --- | --- | --- |
| 0 to 2 | Choose the problem, define the demo path, assign owners | One sentence problem statement and a sketch of the demo |
| 2 to 4 | Set up the repository, test every external dependency | All APIs, data and devices proven to work |
| 4 to 20 | Build the core flow end to end, however rough | A judge could click through the main path |
| 20 to 28 | Sleep in shifts, then fix what broke and connect the pieces | The core path works on one shared build |
| 28 to 40 | Improve the experience along the demo path only | The demo looks and feels intentional |
| 40 to 44 | Feature freeze, write the submission, record the video | Draft submission saved with video and screenshots |
| 44 to 47 | Rehearse the pitch, fix only demo-breaking bugs | Two clean run-throughs in a row |
| 47 to 48 | Submit, then check the submission page | Submission confirmed before the deadline |

## Hours 0 to 4: decide and de-risk

Spend the first hours deciding, not coding. Agree on the [problem](/guides/pick-a-problem-statement/), then describe the demo path: the exact steps a judge will see. Everything you build should serve that path.

Then test every dependency. If an API needs approval or a dataset is unusable, you want to know now.

## Hours 4 to 20: get something working end to end

Build a thin version of every step in the demo path before polishing any one step. A rough end-to-end flow tells you where the real problems are. Merge often so integration happens continuously, not at the end.

## Hours 20 to 28: sleep, then integrate

Sleep matters. Tired teams make slow decisions and fragile code. Sleep in shifts if you must, but make sure everyone gets some. When you are back, fix what broke overnight and get the core flow running on one shared build.

## Hours 28 to 40: polish what judges will see

Now improve the experience, but only along the demo path. Clear labels, sensible sample data and a layout that works on the screen you will present from count for more than hidden features.

Keep a "not doing" list. Every idea that comes up goes on it unless it improves the demo.

## Hours 40 to 44: freeze and write

At a fixed time, stop adding features. From here on, only fix bugs that break the demo.

Write the submission while you still have energy. Most platforms ask for a project name, a one-line tagline, a description, the technologies used, links and a demo video. On Devpost you can keep editing your project until the submission deadline, so save a complete draft early rather than waiting for the perfect version. The [Devpost](/guides/apply-on-devpost/) and [Devfolio](/guides/apply-on-devfolio/) guides list each platform's steps.

Record the demo video now, while the build is stable. A recorded video is also your backup if the live demo fails.

## Hours 44 to 48: rehearse and submit

Run the pitch from start to finish at least twice, with a timer. Then [submit](/guides/apply-on-devpost/), open your submission page and check that the video plays, the links work and every teammate is listed.

Aim to submit an hour early. Upload slowdowns, last-minute errors and forgotten required fields are common in the final minutes.

## Rules that save weekends

- **Decide early, build late.** Arguments are cheaper in hour one than in hour thirty.
- **One path, done well.** Breadth looks impressive on a slide and fragile in a demo.
- **Freeze on time.** The best last-minute feature is the one you did not add.
- **Eat, drink water, sleep.** You will present better and write better code.

When the demo works, read [how to build a demo that lands](/guides/build-a-demo-that-lands/) and [how to pitch to judges](/guides/pitch-to-judges/).
